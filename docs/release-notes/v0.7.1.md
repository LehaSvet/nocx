# nocx 0.7.1

0.7.0 broke the first command for some zsh setups and could not start an agent the
pane itself could find. This patch fixes those, plus two ways a block could show
something that was not its own output.

## Your shell integrates again, and `claude` starts

If your `.zshrc` was written by an earlier nocx, it still sources nocx's shell
integration — and since 0.6.1 that happened twice, which left the shell connected
but inactive: a command's block stayed Running with no way out, and `claude` said
the pane had no lifecycle channel. The integration now establishes its channel
once, whichever order the two loads happen in, and `claude` in a pane that cannot
be orchestrated runs your real agent anyway instead of refusing.

You no longer need to remove the nocx line from your shell startup file, and nothing needs
a full path.

## An agent starts even when the app cannot see it

Starting `claude` failed with "the local agent executable could not be resolved"
when nocx could not find it — an app opened from Finder sees a much smaller `PATH`
than your shell does. nocx now asks the pane where the program is, and starts that.

Putting a full path into the agent record is no longer necessary.

## A full-screen program's block shows its own output

Over ssh, the block for a full-screen program such as `htop` could complete
showing earlier commands' rows — a previous listing, or the screen of a TUI that
had already exited. The block now ends where the program's own output ends.

## A burst of lost output is one notice, not a wall of cards

When live output is lost, nocx used to stack a card per event and keep them. It now shows one
bounded notice with a running total, and the notice leaves on its own instead of pushing the
terminal away.

## What 0.7.1 does not include

Signed nightly builds remain in 0.8.
